# 星图立项与数据模型（2026-11-04）

> 决策记录：为什么叫星图、为什么只存本机、仓库状态怎么算、批量操作为什么这么设计。
> 代码位置见各节末尾的引用；实现变更时请同步本文档，别让它变成历史遗迹。

## 一、命名

| 项 | 值 | 理由 |
|---|---|---|
| 项目名 / Go module | `bestuav-atlas` | 小写、可作目录名与 module 路径；`bestuav-` 与家族其它项目一致 |
| 品牌 | 星图 | atlas = 图册：项目是疆域、仓库是地标、待办是坐标点；与「量子科学」「花火」的天文意象一脉 |
| 应用标识 | `com.bestuav.atlas` | 反向域名；**不要**用脚手架推导出的 `com.bestuavatlas`（去中划线后的丑值） |
| 仓库 | `lark203/bestuav-atlas` | 与 `bestuav-mygo`、`bestuav-hanabi` 同一个 GitHub 账号 |

改名时三处要一起动：`internal/appmeta/appmeta.go`（Name/Title/Identifier）、`mygo.json`（name/identifier/slug）、
以及用户配置目录 `%APPDATA%\bestuav-atlas\`（改名等于让老配置失效，需要迁移）。

## 二、范围

三块功能，一个窗口：

1. **待办**：人手写的轻量清单（无审批、无流程），可挂项目与仓库；
2. **项目**：仓库与待办的归属单位；
3. **仓库**：多个 GitHub 仓库的本地状态总览 + 批量操作。

明确不做（本版）：

- 不做 Issue / PR 的拉取与看板（GitHub 只在「读仓库列表」「刷新远端信息」时调用）；
- 不做自动定时 fetch（产品约束：联网必须由用户点按钮触发）；
- 不做 git 凭据管理：推送用本机已配置的 `git` 凭据，星图不存用户名密码；
- 不与 bestuav 主工程的 `sys_todo` 或工作流引擎互通（语义不同，见 README 第十一节）。

## 三、存储

- SQLite（`modernc.org/sqlite`，纯 Go、无 cgo），文件在系统用户配置目录下；
- 单连接（`SetMaxOpenConns(1)`）串行化所有访问，桌面单用户场景下不需要连接池；
- 时间统一存 **UTC RFC3339Nano 字符串**，零值存空串；读出时 `parseTime("")` 得零值；
- schema 版本记在 `schema_meta`，当前 **3**（1=任务/授权/事件，2=页面状态，3=项目/仓库/待办）。

表结构见 `internal/store/atlas.go` 与 `README 第七节`。两个约定：

- **删除项目不删仓库**：`DeleteProject` 在事务里把 `repo.project_id` / `todo.project_id` 置 0，
  再删项目——代码登记与待办是用户的资产，不该因为删了个分组就消失；
- **状态列是缓存**：`status / status_msg / dirty / ahead / behind / last_commit / checked_at`
  全部可由一次 `gitx.Inspect` 重算，`SaveRepoStatus` 只写这几列，不碰用户手填的字段。

## 四、仓库状态的判定

状态是**算出来的**，不是用户填的。优先级（`internal/view/atlas_data.go`）：

```
待提交  ← dirty > 0
  ↓ 否则
需要更新 ← behind > 0
  ↓ 否则
待推送  ← ahead > 0
  ↓ 否则
正常
```

另有两种「非 git 状态」：`未克隆`（没设目录/目录不存在）、`错误`（目录不是 git 仓库等）。

为什么「待提交」排最前：有本地改动时先拉取极容易冲突，应该先处理自己的改动；
为什么「落后」排在「领先」前：同步之后再推，避免推上去又立刻落后。

**已知局限**：ahead/behind 是相对「上次 fetch 的远端引用」算的，不是实时远端。
所以表格里同时显示检查时间，并把手动「批量拉取」放在显眼位置——把「数据可能陈旧」
这件事摆在界面上，而不是假装实时。

## 五、批量操作

| 动作 | 实际命令 | 关键取舍 |
|---|---|---|
| 刷新状态 | `git status --porcelain` / `rev-list --left-right --count` | 纯本地，毫秒级，几十个仓库也无所谓 |
| 批量拉取 | `git fetch --prune` + `git pull --ff-only` | `--ff-only` 保证不产生合并提交；分叉时直接报错，让人来处理 |
| 批量提交并推送 | `git add -A` + `git commit -m` + `git push` | 无改动跳过 commit 仍执行 push（补推上次失败的推送） |
| 刷新远端信息 | `GET /repos/{owner}/{repo}` | 只有这个动作会调 GitHub API，且需要令牌 |

串行执行、单仓库 90 秒超时、失败不中断其余仓库；结束后汇总成一条「成功 N / 失败 M」
写进异步任务记录。串行的理由：`.git/index.lock` 会让并发 git 互相踩，且批量操作
本来就不是性能敏感场景。

**风险提示**：批量提交会把选中仓库里**所有**未提交改动一并提交并推到当前分支。
确认弹窗里有红字说明，提交说明可改；这是有意为之——批量场景下逐个确认反而更容易误点。

## 六、可观测性与失败处理

- 每次写库失败都 `logging.Errv` 一条，界面上 toast 提示，不静默吞；
- 批量任务的每一步都记仓库名与错误摘要，失败详情进日志；
- 数据库打不开时（安全模式/首次启动失败）页面不变成错误页，而是顶部一条提示 +
  空数据，改动只在内存里——「看得见全局」比「严格失败」对这个工具更重要。

## 七、后续可做

1. 仓库分组/标签（现在只有「项目」一层归属）；
2. 待办的重复规则与提醒（本地通知已具备）；
3. GitHub Issue ↔ 待办的手动导入；
4. 多设备同步沿用 mygo 底座的「配置包 + 仓库托管」，但要注意令牌不随包导出。
